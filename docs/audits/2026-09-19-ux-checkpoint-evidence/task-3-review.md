# Task 3 independent review

## Verdict

Task 3 is **not ready to accept**. The storage recovery, sign-out disclosure, provider cancellation/error handling, transaction dismissal guard, confirmed-entitlement checks, remote-alert honesty, and basic in-app help are present. However, several explicit acceptance criteria remain incomplete, including a severe native paywall regression.

## Important findings

1. **The Arena paywall is illegible and its main purchase controls are not exposed correctly to assistive technology.** `components/PaywallModal.tsx:182-235, 251-322, 414-498` changes the page to the light Arena palette but leaves feature cards, benefit titles, subtitles, plan labels, and prices on hard-coded colors intended for the old dark page. In the native capture `/tmp/puckiq-ux-paywall.jpg`, benefit titles disappear, subtitles and plan labels are very low contrast, and both prices are white on pale cards. The CTA also combines a team-dependent gradient with `palette.actionInk`; its right side is dark while the label remains dark. Native screen mapping identifies Purchase help as a button but does not identify the plan choices, Subscribe, or Restore Purchases as controls. This fails Arena consistency, legibility, and accessible-controls acceptance. Fix by applying `palette.paper/soft/edge/ink/muted/link` to every card and text role, using one action surface whose ink token is guaranteed for that surface, and adding explicit roles, labels, selected/disabled state, and adequate targets to close, plan choices, Subscribe, and Restore. Validate across neutral plus light/dark team palettes in native iOS and Android.

2. **The paywall still markets ungated forecast value as a Pro benefit.** `components/PaywallModal.tsx:218-220` says Pro provides “model-backed probabilities,” and `components/PremiumGate.tsx:86-89` says Pro adds “forecast ... tools.” The concrete gates found in the app are Fantasy Projections (`app/(tabs)/players.tsx:621`) and My Team (`components/MyTeamScreen.tsx:112`); the shared benefit policy itself lists only player analytics and My Team (`utils/accountFlowPolicy.ts:25-28`). Published model-backed game probabilities are not shown to be gated. This violates the ruling that marketing match actual gates. Remove the forecast/probability claims or identify and test the concrete entitlement gate that makes them true. Use the same shared policy copy in both the modal and gate.

3. **A valid but empty RevenueCat offering has no retry action.** `components/PaywallModal.tsx:103-106, 242-249` renders only “Subscriptions are currently unavailable” when `offerings.current` is missing or has no priced packages. The Retry button appears only when `getOfferings()` throws. Closing and reopening happens to rerun the effect, but there is no discoverable inline recovery and Purchase help tells the user to retry a store connection without providing that action. The requirement is offering retry and offseason/unavailable reachability. Render the same retry control for `unavailable` and `error`, and test empty current offerings and offerings with zero supported packages.

4. **Settings origin is not persisted for cold restoration.** `components/HubScreen.tsx:168-171` can consume an `origin` parameter, but the only production entry found, `components/arena/ArenaPrimitives.tsx:130-134`, pushes `/(tabs)/hub` without one. Normal Back works while history remains, but after restoration/cold entry on Settings the fallback always resolves to Tonight. Therefore Following, Players, and League origin cannot be preserved as specified. Pass the current allowed route as the origin when opening Settings (or store it in navigation state), and add integration tests for each source plus direct/cold entry fallback.

5. **Settings authentication does not expose a visible busy state.** `components/HubScreen.tsx:160-166, 273-291` disables both provider buttons but leaves their labels and styling unchanged and renders no progress text/indicator. A pending native/browser flow therefore looks tappable even though presses are ignored. The report’s claim that busy state is visible is not supported by source or tests. Show provider-specific progress (for example, “Opening Google…” with an activity indicator), add `accessibilityState={{ disabled: true, busy: true }}` while pending, and test the state before resolving the auth promise.

## Minor findings

1. **Support recovery instructions are not directly actionable from the help surface.** `components/HubScreen.tsx:312-320` tells the user to open Subscription options and return to Tonight, but offers only Contact support (when configured) and Close help. Add “Subscription options” and “Go to Tonight” actions so the in-app fallback performs the recovery it describes. Also handle `Linking.openURL` rejection with visible feedback; current `void Linking.openURL(url)` can fail silently (`components/HubScreen.tsx:173-179`).

2. **The launch recovery UI only partially follows Arena/accessibility roles.** `app/_layout.tsx:45-46` hard-codes cyan, has no palette surface/ink roles, and does not mark the failure heading or error text semantically. It does provide the required visible retry and preserves data, so this is not a functional blocker. Render it from Arena palette/type roles and mark the heading/error appropriately.

## Evidence limits

The source establishes the dismissal guard and structured purchase/restore outcomes, but it cannot establish native store-sheet behavior, VoiceOver/TalkBack behavior, dynamic type, Android Back behavior, or live Apple/Google auth. Those still require the controller’s device pass. I did not rerun the already reported 55 focused tests or broad repository tests, per review instructions.
