# Task 1 independent review — Players and Following

## Verdict

**Spec: fail. Quality: fail pending important fixes.** The search session, arbitrary-player watch action, persisted mutation ordering, Following collection, My Team entry, origin parameter, and most action labels are useful improvements. Task 1 is not complete because F09 still reports backend failures as valid empty/not-found states, the hook can regress subscribed state through an uncoordinated read race, and Following has a real double-tap removal race that destroys Undo. The focused tests cover two service helpers, but do not exercise the screen/hook failure and race behavior required by the acceptance criteria.

## Important findings

1. **F09 is still unfixed for the feed and detail paths.** `loadTrendingData()` can only render its new error state when a dependency throws (`app/(tabs)/players.tsx:131-189`), but the dependencies deliberately absorb failures: `seasonRows()` returns `null` for Supabase errors (`services/playerTrends.ts:155-165`), `getLeagueLeaders()` converts that and every thrown exception to `[]` (`services/playerTrends.ts:243-260`), `getTrendingPlayers()` does the same (`services/playerTrends.ts:285-293`), and tonight/projection paths similarly return empty collections (`services/playerTrends.ts:316-340`, `services/playerTrends.ts:481-484`). An offline initial load therefore still looks like a valid empty feed and the Retry CTA never appears. Player detail has the same defect: the required bio query maps both a missing row and any backend error to `null`, and the outer catch also returns `null` (`services/playerDetail.ts:234-280`), so `PlayerDetailModal` labels an offline/backend failure as “Player not found” (`components/PlayerDetailModal.tsx:80-90`). Preserve a typed unavailable/error outcome (or throw on backend error while retaining a distinct not-found result) through these service boundaries and test the rendered feed/detail retry behavior.

2. **Independent hook refreshes can overwrite a newer subscription update with stale persisted data.** Every `useWatchlist()` instance subscribes and immediately calls `readWatchlist()` (`hooks/useWatchlist.ts:16-28`), while reads are outside the mutation queue (`services/watchlist.ts:38-40`, `services/watchlist.ts:57-60`). The Players feed creates a hook for every elevated row and the detail modal, and Following also refreshes on focus. If one of those reads begins before a mutation, then resolves after `persist()` publishes the successful new snapshot, that hook calls `setPlayers()` with the older snapshot and disagrees with the other rows/count until another refresh or mutation. This violates the required subscription/update consistency and can visibly undo a successful Watch state. Centralize the in-memory snapshot/initialization or version/serialize reads with mutations, then add a deferred-read test proving a late refresh cannot replace a newer persisted notification.

3. **A double tap on Following remove can erase the only Undo snapshot.** The remove control has no busy state or disabling (`app/(tabs)/following.tsx:126-131`). Two presses enqueue two serialized removes: the first removes the record and sets `removedPlayer` to it; the second reads the now-empty list, returns `null`, and then calls `setRemovedPlayer(null)`. The player is gone and Undo disappears. Disable per-player removal while pending (and give it busy accessibility state), or ignore a null second result; cover this exact interaction with a behavioral test.

4. **Writing the new object array to the established key is not backward compatible with the shipped reader.** The new reader accepts legacy `number[]`, but every mutation rewrites `puckiq_watchlist` as `WatchedPlayer[]` (`services/watchlist.ts:63-83`). Baseline/shipped `ElevatedPlayerRow` parsed that key as IDs and used `ids.includes(playerId)`, and baseline Following counted only numeric entries. A rollback or older binary reading storage after the upgrade will treat all object records as unwatched/zero. Repository search found no remaining current-code consumer outside the new service, so current-forward compatibility is covered; deployed-version compatibility is the remaining named risk. Preserve the numeric key and store metadata separately, or document and explicitly accept the irreversible storage migration with a safe compatibility strategy.

## Minor findings

1. Watch failure state in `PlayerDetailModal` is component-wide and is not reset when a different player opens (`components/PlayerDetailModal.tsx:62-64`, `components/PlayerDetailModal.tsx:68-112`). After a failed write, closing and opening another player labels that unrelated action “Retry updating watchlist.” Reset `watchError`/`watchBusy` for each visible player session.

2. Following’s remove failure copy says “Retry,” but it provides no explicit retry control or retry-specific accessibility label; the unchanged close icon is the only way to try again (`app/(tabs)/following.tsx:130`, `app/(tabs)/following.tsx:154`). Make recovery discoverable and keep the target record captured for retry.

3. The new tests are mostly helper-level and miss the actual journey. `playerSearchSession.test.ts` meaningfully verifies generation ordering and success/error distinction, and `watchlist.test.ts` meaningfully verifies serialized toggles and publish-after-write. There is no behavioral coverage for one-character input remaining mounted, query-preserving Retry, feed/detail backend errors, hook reactivity/read races, Following removal/Undo, or opening a saved player and unwatching from detail. The existing `arenaPrimaryScreens.test.ts` only searches source strings, and the older Players test mocks obsolete service APIs, so neither substantiates these acceptance paths.

## Confirmed strengths and remaining runtime checks

- Search stays active below two characters and generation cancellation prevents an old search result from replacing the latest query (`app/(tabs)/players.tsx:236-270`). Closing detail leaves the parent search state intact.
- Successful watchlist writes publish only after storage succeeds, mutations are serialized, and legacy numeric IDs remain readable in the new app (`services/watchlist.ts:17-34`, `services/watchlist.ts:48-84`).
- Any player reachable through search/feed cards can open detail and use the same watch action; Following displays saved records, opens detail, offers removal/Undo, explains device-local persistence, and links to My Team.
- Arena palette roles are used for the changed top-level surfaces, with explicit labels on the principal actions and 48-point targets on detail/watch/removal controls. Native iOS/Android focus return, 320-wide layout, 200% Dynamic Type, screen-reader announcements, and reduced-motion behavior remain controller checks as assigned.
